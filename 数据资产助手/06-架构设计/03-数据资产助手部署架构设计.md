# 03 数据资产助手部署架构设计

## 1. 设计目标

本文档用于说明数据资产助手在公司内部测试环境、生产环境中的部署方式，以及与现有数据资产管理平台、公司内网大模型、调度平台、可观测与评测平台的分环境对接关系。

部署架构重点回答以下问题：

1. 数据资产助手服务部署在哪里。
2. 测试环境和生产环境如何隔离。
3. 生产正式接口在核心网时，助手如何访问。
4. Prompt Router / Control Mode Router 等多主控能力如何分环境部署和验证。
5. 调度系统如何承接异步轮询、失败补偿和超时提醒。
6. 大模型、可观测与评测平台如何按环境接入。
7. Demo、联调、正式投产之间如何平滑演进。

## 2. 当前环境约束

| 约束项 | 说明 | 对助手设计的影响 |
| --- | --- | --- |
| 公司内部有测试环境和生产环境 | 两套环境都需要部署助手侧服务 | 需要按环境维护配置、密钥、模型地址、观测地址、数据库连接 |
| 正式接口在生产环境 | 生产 Agent 网关、Java API、ES、Activiti、Oracle / GoldenDB 主要在生产环境 | 生产助手调用正式接口，测试助手默认不直接调用生产正式接口 |
| 正式接口部署在核心网 | 生产能力有网络边界和访问控制 | 助手生产服务需要通过受控网络策略访问核心网接口 |
| 调度平台分环境管理 | 测试与生产调度任务、作业参数、告警接收人必须隔离 | 助手侧调度任务需要按环境注册，禁止测试任务轮询或补偿生产任务 |
| 测试环境仅用于测试和联调 | 测试环境不能代表完整生产数据、权限和接口能力 | Demo 阶段优先使用 Agent 网关 Mock、Mock Tool、测试数据、受控联调接口 |
| 大模型有测试和生产环境 | 内网私有化大模型按环境部署 | 测试助手调用测试大模型，生产助手调用生产大模型 |
| 可观测与评测平台有测试和生产环境 | 公司可观测与评测平台基于 OpenTelemetry 封装，并使用 Langfuse | Trace、Prompt、LLM 调用、Tool 调用日志、评测样例和效果指标必须进入对应环境的可观测与评测平台 |

## 3. 总体部署分区

### 3.1 测试环境

测试环境用于 Demo、功能验证、联调验证和灰度前验收。

建议部署组件：

| 组件 | 部署建议 | 说明 |
| --- | --- | --- |
| 数据资产助手 AI 服务 | 测试环境部署 | FastAPI + LangGraph 多主控主图 + Prompt Router + Control Mode Router + Tool Adapter |
| Agent 网关 Mock / 测试 Agent 网关 | 测试环境部署 | Demo 阶段可先使用 Mock，后续切换为测试 Agent 网关 |
| Mock Tool / 测试 Tool | 测试环境部署 | 模拟数据地图、血缘、安全扫描、数据标准等接口 |
| 测试调度任务 | 测试 XXL-JOB / 现有测试调度平台 | 模拟或验证异步轮询、失败补偿、超时提醒 |
| 助手库表 | 测试 GoldenDB 或测试库 Schema | 保存会话、确认记录、任务状态、偏好记忆 |
| Redis | 测试 Redis | 保存短期会话状态、LangGraph Checkpoint、待确认上下文 |
| 测试大模型 | 测试模型环境 | 用于提示词、Tool Calling、结构化输出验证 |
| 测试可观测与评测 | 测试 OpenTelemetry / Langfuse / 评测数据集 | 记录测试 Trace、评测样例、回归结果、Prompt 调优记录 |

测试环境原则：

1. 默认不直接调用生产核心网正式接口。
2. 如确需联调生产正式接口，必须通过受控白名单、生产 Agent 网关、只读或低风险接口策略执行。
3. 测试环境禁止误写生产数据。
4. 测试调度任务只能指向测试助手库表、测试 Redis、Mock Tool 或受控测试接口。
5. 测试环境使用独立的模型配置、观测项目、评测数据集、数据库 Schema、Redis Namespace。
6. 测试数据、Mock 数据、生产脱敏样本需要明确标识来源。
7. 测试评测集可以包含人工标注样例，但不得混入未脱敏生产明细。

### 3.2 生产环境

生产环境用于正式用户访问和真实业务办理。

建议部署组件：

| 组件 | 部署建议 | 说明 |
| --- | --- | --- |
| 数据资产助手 AI 服务 | 生产服务区部署，具备访问核心网接口的受控通道 | FastAPI + LangGraph 多主控主图 + Prompt Router + Control Mode Router + Tool Adapter |
| Agent 网关 | 生产核心网或现有生产访问区 | 统一登录、Token 获取、用户身份透传、权限边界 |
| 现有 Java API | 生产核心网 | 数据地图、数据源、血缘、标准、安全扫描、流程等既有能力 |
| ES 数据地图搜索引擎 | 生产核心网 | 元数据采集后进入 ES，用于提升数据地图检索速度 |
| Oracle / GoldenDB | 生产核心网 | 数据资产管理平台后端数据库，当前 Oracle 迁移 GoldenDB |
| Activiti 流程引擎 | 生产核心网 | 元数据治理等场景提交流程实例 |
| 生产调度任务 | 生产 XXL-JOB / 现有生产调度平台 | 负责长流程轮询、失败补偿、超时提醒、批量任务触发 |
| 助手库表 | 生产 GoldenDB 或独立助手库 | 保存助手会话、任务、记忆、确认、审计映射 |
| Redis | 生产 Redis | 保存运行态、Checkpoint、短期上下文 |
| 生产大模型 | 生产模型环境 | 支撑正式问答、Tool Calling、结构化生成 |
| 生产可观测与评测 | 生产 OpenTelemetry / Langfuse / 效果指标 | 记录正式链路 Trace、模型调用、Tool 调用、异常排查数据和人工反馈指标 |

生产环境原则：

1. 用户从现有数据资产管理平台入口进入。
2. 通过 Agent 网关登录接口获取 Token，并向助手服务透传用户身份。
3. 助手服务调用 Tool Adapter，Tool Adapter 再调用现有 Java API。
4. 正式业务写操作必须保留用户确认、流程提交、审计记录。
5. 生产调度任务只推进已落库的 `agent_task`，不直接绕过助手服务调用大模型或发起写操作。
6. 内网登录密码、Token、敏感字段在进入可观测与评测平台前必须脱敏。
7. 生产助手只连接生产大模型、生产可观测与评测、生产 Redis、生产助手库表和生产调度平台。
8. 生产评测只保存脱敏问题摘要、外部对象引用、人工反馈和指标结果，不保存真实业务明细样本。

## 4. 环境隔离策略

| 隔离对象 | 测试环境 | 生产环境 | 隔离要求 |
| --- | --- | --- | --- |
| 服务地址 | 测试域名 / 测试网关 | 生产域名 / 生产网关 | 通过环境变量或配置中心区分 |
| 大模型 | 测试模型 Endpoint | 生产模型 Endpoint | 禁止测试请求误发生产模型 |
| 可观测与评测 | 测试 Langfuse Project / 测试评测集 | 生产 Langfuse Project / 生产效果指标 | Trace、Prompt、评测数据、反馈指标分环境 |
| 数据库 | 测试助手库表 | 生产助手库表 | 库、Schema 或租户标识隔离 |
| Redis | 测试 Redis / Namespace | 生产 Redis / Namespace | Key 前缀按环境隔离 |
| 调度平台 | 测试调度任务 / Mock 定时器 | 生产调度任务 | 作业 ID、执行参数、告警接收人按环境隔离 |
| Tool 接口 | Mock / 测试接口 / 受控联调接口 | 生产 Java API | 测试默认不直连生产正式接口 |
| 密钥 | 测试密钥 | 生产密钥 | 密钥分环境托管，禁止混用 |
| 审计 | 测试审计 | 生产审计 | 生产审计必须可追溯到用户身份和流程实例 |

建议引入统一环境配置：

```yaml
env: test | prod
agent_gateway:
  base_url: ${GATEWAY_BASE_URL}
llm:
  endpoint: ${LLM_ENDPOINT}
observability:
  otel_endpoint: ${OTEL_EXPORTER_OTLP_ENDPOINT}
  langfuse_project: ${LANGFUSE_PROJECT}
assistant_db:
  dsn: ${ASSISTANT_DB_DSN}
redis:
  url: ${REDIS_URL}
  key_prefix: data_asset_assistant:${ENV}:
scheduler:
  enabled: true
  platform: xxl-job | platform-scheduler | mock
  admin_url: ${SCHEDULER_ADMIN_URL}
  app_name: data-asset-assistant-${ENV}
  job_group: ${SCHEDULER_JOB_GROUP}
tool:
  mode: mock | test | prod
control_mode:
  default: tool_query
  enable_agentic_loop: true
  enable_streaming: true
  loop_max_steps: 8
  readonly_tool_only_in_loop: true
```

## 5. 调用链路设计

### 5.1 测试链路

```text
测试用户
  -> 测试入口 / Agent 网关 Mock
  -> 数据资产助手测试服务
  -> Prompt Router / Control Mode Router
  -> LangGraph 多主控编排
  -> LangChain Core 模型与 Tool Calling 适配
  -> Mock Tool / 测试 Tool
  -> 测试调度任务 / Mock 定时器
  -> 测试数据 / 测试接口
```

旁路能力：

1. 助手测试服务调用测试大模型。
2. 助手测试服务写入测试 Redis 和测试助手库表。
3. Prompt Router / Control Mode Router 在测试环境验证 Skill 问答、单次 Tool、固定状态机、Agentic Loop、流式生成、人工确认等路径。
4. 测试调度任务按测试命名空间读取 `agent_task`，验证轮询、补偿、超时提醒。
5. OpenTelemetry Trace 上报到测试可观测与评测平台。
6. Langfuse 记录测试 Prompt、LLM 调用、Tool 调用、主控模式路由和评测数据。
7. 测试评测集记录标准问题、权威资产、标准答案和人工标注结果，用于版本回归。

### 5.2 生产链路

```text
正式用户
  -> 现有数据资产管理平台
  -> 生产 Agent 网关
  -> 数据资产助手生产服务
  -> Prompt Router / Control Mode Router
  -> LangGraph 多主控编排
  -> LangChain Core 模型与 Tool Calling 适配
  -> Tool Adapter
  -> 生产 Java API
  -> ES / Oracle / GoldenDB / Activiti
  -> 生产调度平台
```

旁路能力：

1. 助手生产服务调用生产大模型。
2. 助手生产服务写入生产 Redis 和生产助手库表。
3. 生产任务落库时记录 `prompt_type`、`control_mode` 和关键 `agent_task_step`。
4. OpenTelemetry Trace 上报到生产可观测与评测平台。
5. Langfuse 记录生产 Prompt、LLM 调用、Tool 调用、主控模式路由、异常和评测数据。
6. 生产效果指标按采纳、修改、驳回、审批通过、审批退回计算，不直接暴露明细样本。
7. 写操作通过 Activiti 流程引擎落地，并保留用户确认与审计记录。
8. 长流程状态由生产调度平台轮询和补偿，任务主状态回写生产助手库表。

## 6. 核心网访问设计

生产正式接口部署在核心网，因此数据资产助手生产服务需要采用受控访问方式。

建议策略：

| 策略 | 建议 |
| --- | --- |
| 网络访问 | 生产助手服务通过生产 Agent 网关或受控服务网关访问核心网 Java API |
| 接口白名单 | 仅开放助手需要调用的数据地图、数据源、血缘、标准、安全扫描、流程接口 |
| 身份透传 | 使用 Agent 网关 Token 和用户身份，避免助手绕过平台身份体系 |
| 写操作控制 | 发起治理、流程提交、安全等级确认等操作必须有人机确认 |
| 调度控制 | 调度任务只处理已落库任务状态，失败补偿必须有最大重试次数和告警 |
| 数据脱敏 | 账号、密码、Token、敏感字段进入日志和观测前脱敏 |
| 主控模式控制 | Agentic Loop 只允许只读 Tool，写操作必须转人工确认或固定状态机 |
| 降级策略 | 核心网接口不可用时，助手返回可解释的失败原因和下一步建议 |

## 7. 发布与演进路径

### 阶段 1：Demo 验证

目标：验证 LangGraph 多主控编排、Tool Calling、元数据治理流程、可观测与评测链路。

部署方式：

1. 测试环境部署 FastAPI 数据资产助手服务。
2. 使用 Agent 网关 Mock。
3. 使用 Mock Tool 和 Mock 数据。
4. 验证 Prompt Router / Control Mode Router 可区分 Skill 问答、单次 Tool、固定状态机、Agentic Loop、流式生成和人工确认。
5. 使用 Mock 定时器或测试调度任务模拟轮询、补偿、超时提醒。
6. 接入测试大模型。
7. 接入测试 OpenTelemetry / Langfuse。
8. 准备测试评测集，覆盖意图识别、查表推荐、元数据补全、安全等级推荐和血缘解释。

### 阶段 2：测试联调

目标：接入真实测试接口或受控联调接口，验证端到端链路。

部署方式：

1. 测试助手服务接入测试 Agent 网关。
2. Tool Adapter 对接测试 Java API 或受控联调接口。
3. 主控模式路由规则接入测试配置，验证 Loop 只读 Tool 白名单和写操作确认规则。
4. 调度任务接入测试 XXL-JOB / 现有测试调度平台。
5. 助手库表、Redis、可观测与评测、大模型全部使用测试环境。
6. 对生产正式接口联调时，只允许通过受控白名单方式进行。

### 阶段 3：生产试点

目标：在小范围用户和低风险场景中试点。

部署方式：

1. 生产环境部署数据资产助手服务。
2. 通过生产 Agent 网关获取 Token 并透传用户身份。
3. Tool Adapter 调用生产核心网 Java API。
4. 接入生产 Prompt Router / Control Mode Router 配置。
5. 接入生产大模型和生产可观测与评测平台。
6. 接入生产调度平台，注册轮询、补偿、超时提醒任务。
7. 写操作走 Activiti 流程和用户二次确认。

### 阶段 4：规模化推广

目标：覆盖更多数据资产子 Agent 和治理场景。

演进方向：

1. 将稳定 Tool 沉淀为标准工具目录。
2. 将复杂领域能力沉淀为 Skill。
3. 将跨系统、跨团队复用能力逐步演进为 MCP 服务。
4. 将主控模式路由规则配置化，沉淀 Prompt 类型识别、Loop 白名单和写操作确认规范。
5. 将调度任务模板化，沉淀统一的长流程轮询、补偿和提醒规范。
6. 增加多环境灰度、限流、熔断、审计、评测数据集和回归测试。
