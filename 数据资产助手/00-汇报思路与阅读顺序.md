# 00 数据资产助手汇报思路与阅读顺序

本文用于组织数据资产助手方案汇报材料，面向“为什么建设、建设成什么样、如何架构落地、先落哪个能力”四个核心问题展开。

## 1. 汇报主线

建议用一句话开场：

```text
数据资产助手不是再做一个聊天机器人，而是在数小智体系下，把数据资产管理平台里分散的查、看、补、审、提交流程，用 Agent 编排成一个可交互、可确认、可追踪的智能治理入口。
```

整场汇报建议按以下逻辑推进：

```text
为什么需要资产助手
  -> 资产助手应该是什么样子
  -> 它和数小智、现有数据资产平台是什么关系
  -> 它的应用架构和技术选型是什么
  -> 它如何管理用户、资产、任务、证据、记忆和统一知识库上下文
  -> 为什么首期选择数据治理专家的智能元数据补全能力
  -> Demo 如何证明这条链路能跑通
  -> 后续如何从 Mock Demo 演进到生产试点
```

## 3. 第一部分：资产助手应该是什么样子，以及为何是这个样子

核心观点：

```text
数据资产助手 = 数小智下的数据资产领域专家助手。
它不是替代数据资产管理平台，也不是单纯问答机器人。
它是在现有数据资产平台能力上增加一层 AI 编排、工具适配、人工确认和状态跟踪能力。
```

为什么需要这样设计：

1. 数据资产管理诉求天然跨系统：数据地图、元数据、标准、血缘、安全、稽核、流程、调度。
2. 用户的问题通常不是单次问答，而是“查清楚、给建议、让我确认、帮我提交”的连续任务。
3. 大模型擅长理解和生成，但不能单独承担权限、状态、审计和流程责任。
4. 因此需要 Agent 编排把大模型、业务专家 Agent、Tool、状态中心和业务流程连接起来。

建议讲法：

```text
大模型是理解和生成能力，Agent 编排是让这个能力安全调用企业系统的操作系统。
```

## 4. 第二部分：资产助手的架构设计与技术选型

推荐按分层讲：

```text
用户入口层：数小智入口、数据资产助手面板、确认卡片、任务进度。
平台接入层：新建 Agent 网关，负责登录、鉴权、审计和上下文透传。
AI 助手服务层：FastAPI 承接对话、确认、任务查询和响应组装。
上下文管理层：统一组织用户、页面、资产、任务、证据、记忆、知识库召回和权限上下文。
Agent 编排层：LangGraph 承接 Prompt Router、Control Mode Router、专家路由、状态流转和人工确认。
业务专家 Agent 层：数据准备专家、数据开发专家、数据运维专家、数据治理专家、数据安全专家等，每个专家对应一个 Agent。
Tool Adapter 层：统一封装数据源、元数据、指标、建模、血缘、稽核、调度、安全、权限、标准、词根、存储治理等平台能力。
知识库与状态层：统一知识库提供制度、规则、操作指引和历史经验召回；Redis 存短期运行态，GoldenDB 存任务态、确认记录、审计摘要。
可观测与审计层：OpenTelemetry + Langfuse 记录 Trace、Prompt、Tool 调用和反馈。
```

技术选型口径：

| 技术 | 定位 |
| --- | --- |
| 公司内网大模型 | 理解用户问题、生成候选、解释结果 |
| LangGraph | 多主控模式编排、状态流转、人工确认节点 |
| FastAPI | AI 助手服务入口和 Tool Adapter 承载 |
| 统一知识库 | 提供制度规范、操作手册、治理口径、历史经验和 FAQ 等可复用知识 |
| 上下文管理 | 组织用户、资产、会话、任务、证据、知识库召回、记忆和权限边界 |
| Tool Adapter | 对 Agent 暴露稳定工具协议，对下调用现有 Java API |
| Redis | 会话运行态、待确认状态、临时槽位 |
| GoldenDB | 任务状态、用户确认、助手记忆、审计摘要 |
| Activiti | 承接元数据治理等流程提交 |
| 调度平台 | 承接异步轮询、失败补偿、超时提醒、批量触发 |
| OpenTelemetry + Langfuse | 承接链路观测、Prompt 观测和反馈分析 |

## 5. 第三部分：产品形态以及和数小智的关系

关系定位：

```text
数小智是主 Agent，是统一入口、统一路由和结果汇总层。
数据资产助手是数小智下的数据资产领域专家 Agent。
```

产品形态建议讲四种：

1. 对话入口：用户用自然语言发起查表、治理、登记、诊断。
2. 结果卡片：展示候选表、血缘摘要、治理建议、安全风险。
3. 确认卡片：写操作、流程提交、安全等级确认前二次确认。
4. 任务进度卡片：展示数据源登记、元数据采集、安全扫描、治理流程状态。

边界口径：

```text
数据资产助手不替代数小智。
数据资产助手不替代现有数据资产管理平台。
数据资产助手不绕过 Agent 网关、权限、审批和审计。
它负责把现有平台能力用 AI 方式组织成任务闭环。
```

## 6. 第四部分：智能元数据补全作为首期能力

需要先讲清楚分层：

```text
数据治理专家是元数据治理场景的业务负责人和编排者。
智能元数据补全是数据治理专家的一期核心能力。
数据地图、数据标准、词根、血缘和安全扫描是数据治理专家调用的平台能力，不再单独抽象成专家 Agent。
Tool Adapter 是实际调用系统接口的执行层。
```

为什么选择智能元数据补全：

1. 价值直观：减少人工维护中文名、备注、安全等级的成本。
2. 复用范围广：可支撑单表元数据治理、资产盘点、批量补全、元数据质量整改。
3. 风险可控：AI 只生成候选值，不直接发布正式元数据。
4. 证据链完整：每个候选值都有置信度、依据和风险提示。
5. Demo 闭环完整：能展示 Agent 协同、Tool 调用、人工确认和流程提交。

Demo 讲解链路：

```text
用户发起单表元数据治理
  -> 数据治理专家 Agent 接管
  -> 调用元数据查询能力获取表字段上下文
  -> 上下文管理层汇总用户、资产、标准、血缘、安全、历史偏好和任务状态
  -> 调用数据标准和词根能力获取标准映射依据
  -> 调用安全扫描能力获取安全等级建议
  -> 调用血缘查询能力补充上下游依据
  -> 智能元数据补全生成候选值、置信度和依据
  -> 用户确认或修改
  -> 生成治理草案
  -> 提交 Mock Activiti 流程
```

## 7. 建议收尾

建议用这句话收束：

```text
数据资产助手的价值，不是让大模型单独回答数据资产问题，而是让数小智具备一组可调用、可确认、可追踪的数据资产业务专家；首期通过数据治理专家的智能元数据补全能力，先把上下文汇聚、证据补齐、候选生成、人工确认、提交流程这条最小闭环跑通，再逐步扩展到数据准备、数据开发、数据运维、数据安全等完整数据资产场景。
```
