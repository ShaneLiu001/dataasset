# 01 数据资产助手 AI 架构问答知识储备

本文用于沉淀数据资产助手设计过程中反复会被问到的 AI 架构概念、设计口径和落地解释，便于后续汇报、方案评审、团队沟通时复用。

## 1. 为什么现在不强调传统意图识别

### 1.1 问题

为什么现在很多 AI 助手方案里不再把“意图识别”作为核心模块？

### 1.2 核心结论

不是意图识别没有用了，而是它从独立的 `Intent Classifier` 变成了 `Prompt Router + Control Mode Router + Tool Calling + Workflow` 体系里的一个辅助判断。

传统机器人通常是：

```text
用户输入
识别 intent
抽取槽位
进入固定流程
返回结果
```

数据资产助手更适合采用：

```text
用户输入
判断 Prompt 类型、风险等级、关键参数
选择主控模式
执行 Skill / Tool / 状态机 / Agentic Loop / 调度 / 人工确认
返回文本、卡片、表格或任务状态
```

### 1.3 原因

1. 真实用户表达往往不是单一意图，而是混合了目标、背景、现象、限制条件和隐含诉求。
2. 细粒度 intent 数量一多，训练语料、边界规则和冲突处理成本会很高。
3. LLM 可以直接做语义理解、任务拆解、风险判断和工具选择，不再只负责分类。
4. 企业流程更依赖状态、权限、审计和流程节点，而不是只依赖一个 intent 标签。
5. 系统更关心“下一步该调用什么 Tool 或进入什么流程”，而不是只给用户一句话贴标签。

### 1.4 在数据资产助手中的设计口径

数据资产助手可以保留轻量意图判断，但不建立庞大的传统 intent 体系。

推荐口径：

```text
轻量意图识别：负责粗分类、风险识别、入口路由。
Prompt Router：判断用户问题属于说明、查询、办理、诊断、生成、调度、确认还是转交。
Control Mode Router：选择 Skill、Tool、状态机、Loop、流式生成、调度任务、人工确认或子 Agent。
状态机和流程引擎：承接写操作、审批、登记、提交等确定性流程。
```

## 2. 什么是流式生成控制器

### 2.1 问题

应用架构图里的“流式生成控制器”是什么？

### 2.2 核心结论

流式生成控制器是数据资产助手的一种主控模式，负责在证据基本齐全后生成较长的报告、总结、说明或评审口径，并将内容分段返回给前端。

它不是业务系统，也不是 Tool Adapter，而是 AI 助手服务里的输出控制器。

### 2.3 典型场景

```text
生成治理报告
整理评审口径
生成问题诊断总结
输出血缘影响分析说明
生成元数据治理建议说明
```

例如：

```text
用户：帮我生成 dwd_order_detail 这张表的治理评审说明。
```

推荐链路：

```text
Prompt Router 判断为“报告 / 总结 / 说明生成”
Control Mode Router 选择流式生成控制器
前置 Tool / Agent 已拿到表信息、字段问题、标准匹配、安全等级、血缘影响
流式生成控制器组织 Prompt 并调用 LLM
FastAPI 通过 Streaming / SSE 分段返回
前端实时展示生成内容
```

### 2.4 职责边界

流式生成控制器负责：

```text
组织生成上下文
拼装报告生成 Prompt
调用大模型生成长文本
控制输出节奏
把内容通过 Streaming / SSE 返回前端
记录生成 trace 和反馈
```

不负责：

```text
提交审批
修改生产数据
长时间轮询外部系统
自由调用大量 Tool 做动态排查
绕过人工确认执行高风险动作
```

一句话口径：

```text
流式生成控制器是面向长文本生成场景的输出控制器，负责把已有证据组织成报告、总结、说明，并通过流式方式返回给用户。
```

## 3. 什么是 SSE

### 3.1 问题

SSE 是什么？为什么数据资产助手的流式生成可以用 SSE？

### 3.2 核心结论

SSE 是 `Server-Sent Events`，中文可以理解为服务器推送事件。它基于普通 HTTP 连接，由服务端持续向浏览器推送数据。

普通 HTTP：

```text
前端请求
后端处理完成
一次性返回完整结果
```

SSE：

```text
前端请求
后端保持连接
后端持续推送多段内容
前端边接收边展示
```

### 3.3 在数据资产助手中的用法

```text
用户请求生成治理报告
后端开始调用 LLM
LLM 每生成一段内容
FastAPI 通过 SSE 推送给前端
前端逐段展示
生成完成后发送 done 事件
```

示例事件：

```text
event: message
data: 正在整理资产基本信息...

event: message
data: 正在分析字段备注缺失情况...

event: message
data: 正在生成治理建议...

event: done
data: 完成
```

### 3.4 SSE 与 WebSocket 的区别

| 对比项 | SSE | WebSocket |
| --- | --- | --- |
| 通信方向 | 服务端向前端推送为主 | 双向通信 |
| 底层协议 | HTTP | WebSocket |
| 适合场景 | 流式回答、进度推送、日志推送 | 实时协作、双向控制、在线游戏 |
| 实现复杂度 | 较低 | 较高 |
| 浏览器能力 | EventSource 原生支持 | WebSocket 原生支持 |

数据资产助手的流式回答、报告生成、任务进度提示更偏服务端向前端推送，优先用 SSE 更简单。

## 4. Redis 存运行态，为什么 GoldenDB 不直接存

### 4.1 问题

既然 GoldenDB 也能存数据，为什么会话运行态要放 Redis，而不是都放 GoldenDB？

### 4.2 核心结论

GoldenDB 可以存，但不建议把高频、短生命周期、可过期、可重建的运行态主要放 GoldenDB。

推荐分工：

```text
Redis：存正在发生什么。
GoldenDB：存最终发生了什么、需要留痕什么。
```

### 4.3 Redis 适合存什么

```text
当前 thread_id 对应的会话上下文
临时槽位
候选表列表
等待确认的临时状态
本轮 Tool 调用的临时结果
短期任务进度
前端轮询或刷新需要的运行态
```

这些数据通常生命周期短、访问频率高、可设置 TTL、过期后可以重新查询或重新生成。

### 4.4 GoldenDB 适合存什么

```text
用户最终确认记录
治理草案版本
是否点击提交
Activiti 流程实例 ID
任务最终状态
失败原因
审计摘要
助手记忆
用户常用项目、空间、开发账号等偏好
```

这些数据需要持久化、审计、追溯、复盘或支撑报表查询。

### 4.5 推荐落库策略

| 状态类型 | Redis | GoldenDB |
| --- | --- | --- |
| 当前会话上下文 | 是 | 可选摘要 |
| 临时槽位 | 是 | 否 |
| 候选表列表 | 是 | 用户确认后存关键结果 |
| 等待确认状态 | 是 | 重要确认单也存 |
| 用户确认记录 | 可缓存 | 是 |
| 任务最终状态 | 可缓存 | 是 |
| 流程实例 ID | 可缓存 | 是 |
| 审计摘要 | 否 | 是 |
| 助手记忆 | 可缓存 | 是 |
| LLM 中间 token | 通常不存 | 通常不存 |

推荐过程：

```text
会话开始：Redis 建运行态
用户确认：GoldenDB 写确认记录
提交流程：GoldenDB 写 task / process_instance_id
执行中：Redis 缓存进度，GoldenDB 落关键状态
完成或失败：GoldenDB 写最终结果，Redis 设置短 TTL
```

### 4.6 设计口径

```text
Redis 不是替代 GoldenDB，而是承接对话执行过程中的短期运行态。
GoldenDB 不是不能存运行态，而是不适合承接大量高频临时状态。
关键节点需要落库留痕，临时上下文放 Redis 提升性能和清晰度。
```

## 5. 可复用汇报口径

数据资产助手不是传统的“意图识别 + 固定问答”机器人，而是采用多主控模式的 AI 编排架构。

其中：

```text
Prompt Router 负责理解问题类型和风险。
Control Mode Router 负责选择执行模式。
Skill 问答负责规则说明。
单次 Tool 负责明确查询。
固定状态机负责办理、提交、创建、审批等确定性流程。
Agentic Loop 负责诊断、排查、影响分析等路径不确定任务。
流式生成控制器负责报告、总结、说明等长文本生成。
调度任务控制器负责异步等待、批量、定时和补偿。
人工确认控制器负责写操作和高风险动作拦截。
Redis 负责短期运行态，GoldenDB 负责持久任务态、确认、审计和助手记忆。
```

一句话总结：

```text
数据资产助手的核心不是把所有问题都归成 intent，也不是让模型自由执行所有动作，而是把 LLM 的理解和生成能力放到可控的 Tool、状态机、调度、确认和审计体系中。
```
