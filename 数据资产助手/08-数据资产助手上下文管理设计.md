# 08 数据资产助手上下文管理设计

## 1. 设计定位

上下文管理是数据资产助手从“能聊天、能调工具”走向“能处理企业业务任务”的关键环节。

它不等同于 Redis，也不等同于助手记忆，更不等同于知识库本身，而是负责把一次用户请求相关的身份、权限、页面、资产、任务、证据、知识库召回、历史偏好和审计信息组织成可控的上下文包，再交给 LangGraph、子 Agent 和 Tool 使用。

一句话定位：

```text
上下文管理层负责回答：当前是谁、在哪个业务场景、正在处理哪个资产、已经确认了什么、该调用哪些知识、可用证据有哪些、哪些信息不能进入模型。
```

## 2. 为什么需要上下文管理

数据资产助手面对的不是孤立问答，而是跨系统、跨步骤、带权限和审计要求的业务任务。

如果缺少上下文管理，容易出现以下问题：

1. 用户说“这张表”时，助手不知道指的是页面选中的表、刚才确认的表，还是同名候选表。
2. 用户已经确认过空间、项目、开发账号，助手仍然反复追问。
3. 子 Agent 各自查数据，输入结构不一致，结果难以汇总。
4. LLM 拿到过多无关信息，回答变慢、变泛，甚至混入错误证据。
5. Token、连接串、敏感样例值、越权资产信息可能进入模型上下文。
6. 长流程恢复时，只知道 task_id，不知道当时的资产、确认记录和执行状态。

因此，数据资产助手需要把上下文管理作为独立架构能力，而不是把上下文零散放在 Prompt、Tool 入参或 Redis 里。

## 3. 上下文来源

| 上下文类型 | 来源 | 典型字段 | 用途 |
| --- | --- | --- | --- |
| 用户上下文 | Agent 网关 / 登录态 | user_id、user_name、org_id、role_codes、trace_id | 身份透传、权限判断、审计留痕 |
| 页面上下文 | 数据资产平台前端 | 当前菜单、当前页面、选中资产、筛选条件 | 理解“这个表”“当前任务”等指代 |
| 会话上下文 | FastAPI / Redis | thread_id、最近问题、已抽取槽位、候选列表 | 支撑多轮对话和待确认状态 |
| 任务上下文 | GoldenDB / 调度平台 | task_id、task_type、state、process_instance_id | 支撑长流程恢复、进度查询和补偿 |
| 资产上下文 | ES / Java API / Oracle / GoldenDB | asset_id、datasource_id、schema、table、columns | 支撑查表、治理、血缘、标准匹配 |
| 证据上下文 | Tool / 子 Agent | 标准候选、血缘摘要、安全等级、质量结果 | 支撑候选生成和依据解释 |
| 知识库上下文 | 统一知识库 | 制度规范、操作手册、治理口径、FAQ、历史经验、模板材料 | 支撑规则解释、操作指引、候选生成约束和汇报口径复用 |
| 记忆上下文 | 助手库表 / GoldenDB | 常用空间、项目、开发账号、偏好格式 | 减少重复追问，提高办理效率 |
| 权限上下文 | Agent 网关 / Java API | 可访问资产、可执行动作、审批角色 | 防止越权查询和越权操作 |
| 可观测上下文 | OpenTelemetry / Langfuse | trace_id、span_id、model_request_id | 串联链路、定位问题、复盘效果 |

## 4. 上下文管理层职责

### 4.1 汇聚

从 Agent 网关、前端、Redis、GoldenDB、ES、Java API、调度平台和子 Agent 结果中收集本次任务需要的信息。

汇聚时要区分三类信息：

```text
请求原始上下文：用户输入、登录态、页面态。
业务事实上下文：资产详情、标准、血缘、安全、质量、流程状态。
知识库上下文：统一知识库召回的制度、规则、操作指引、FAQ 和历史经验。
历史与偏好上下文：用户常用空间、项目、开发账号、历史确认样本。
```

### 4.2 归一化

将不同系统返回的信息转成统一上下文结构，避免每个子 Agent 都自己理解字段。

推荐统一上下文包：

```json
{
  "trace_context": {
    "trace_id": "",
    "thread_id": "",
    "task_id": ""
  },
  "user_context": {
    "user_id": "",
    "user_name": "",
    "org_id": "",
    "role_codes": []
  },
  "page_context": {
    "current_app": "data_asset",
    "current_page": "",
    "selected_asset_id": "",
    "filters": {}
  },
  "asset_context": {
    "asset_id": "",
    "datasource_id": "",
    "schema_name": "",
    "table_name": "",
    "columns": []
  },
  "task_context": {
    "task_type": "",
    "state": "",
    "confirmed_slots": {},
    "pending_confirm": {}
  },
  "evidence_context": {
    "standard": [],
    "lineage": [],
    "security": [],
    "quality": []
  },
  "knowledge_context": {
    "policies": [],
    "how_to_guides": [],
    "faq": [],
    "historical_cases": []
  },
  "memory_context": {
    "common_space": "",
    "common_project": "",
    "dev_account": "",
    "from_user_preference": false
  },
  "policy_context": {
    "allowed_tools": [],
    "denied_tools": [],
    "need_human_confirm": false,
    "masking_rules": []
  }
}
```

### 4.3 裁剪

不是所有上下文都应该进入模型。上下文管理层需要按照任务类型做选择和压缩。

优先级建议：

```text
当前用户输入
  > 当前已确认对象
  > 当前任务状态
  > 权限与风险策略
  > 与任务直接相关的证据
  > 与任务直接相关的知识库召回
  > 用户偏好
  > 历史会话摘要
  > 扩展背景资料
```

典型规则：

1. 查询类任务优先保留资产标识、查询条件和权限上下文。
2. 治理类任务优先保留资产详情、标准、血缘、安全、历史确认样本和待确认状态。
3. 规则说明类任务优先保留知识库中的制度、操作指引、FAQ 和版本信息。
4. 诊断类任务优先保留失败现象、最近 Tool 调用结果、流程状态和日志摘要。
5. 报告类任务优先保留已确认事实、证据摘要和知识库中的统一口径，不把全部原始明细直接塞给模型。
6. 写操作任务必须保留确认记录、风险等级、执行人和审计字段。

### 4.4 脱敏与隔离

上下文管理层必须在模型调用前做安全处理。

不得进入模型明文上下文的信息：

```text
用户密码
access_token / refresh_token
数据库连接串
API Key / Secret
生产敏感样例值
未经授权的资产明细
超过当前用户权限范围的组织、空间、项目数据
```

敏感字段处理原则：

1. 能不取就不取。
2. 必须取时只给 Tool 使用，不给 LLM。
3. 必须进入模型时先脱敏、采样、摘要化。
4. Langfuse 和日志中只记录摘要、哈希或脱敏值。

### 4.5 传递

上下文管理层对下游只传必要上下文。

```text
Prompt Router：需要用户输入、页面态、粗粒度任务上下文。
Control Mode Router：需要任务类型、风险等级、参数完整性、权限策略。
子 Agent：只拿本专业需要的业务上下文和证据。
Tool Adapter：拿调用接口所需参数、token、trace_id、审计字段。
LLM：拿脱敏后的问题、证据摘要、必要知识片段、输出约束和可解释依据。
```

### 4.6 沉淀

上下文管理层还要决定哪些信息只短暂缓存，哪些信息需要长期留存。

| 信息类型 | 推荐位置 | 说明 |
| --- | --- | --- |
| 最近几轮会话、临时槽位、候选列表 | Redis | 高频、短期、可过期 |
| 待确认状态 | Redis + GoldenDB 摘要 | 用户确认前高频访问，关键确认点需要留痕 |
| 用户最终确认 | GoldenDB | 用于审计、复盘和后续推荐 |
| task_id、流程实例、最终状态 | GoldenDB | 支撑长流程恢复和进度查询 |
| 常用空间、项目、开发账号 | GoldenDB / 助手记忆表 | 用户偏好，长期有效，可编辑 |
| 知识库召回结果 | 不长期固化原文，仅记录引用摘要和知识版本 | 避免把知识库内容复制进任务态，同时保留可追溯引用 |
| Tool 调用摘要 | GoldenDB + OTel | 业务审计和技术排障分开存 |
| Prompt、模型输出、反馈 | Langfuse | 用于模型效果分析，注意脱敏 |

## 5. 在应用架构中的位置

推荐把上下文管理层放在 AI 助手服务层和 Agent 编排层之间，同时连接数据与状态层、现有平台能力层、可观测与审计层。

```text
Agent 网关 / 前端页面
  -> FastAPI AI 助手服务
  -> 上下文管理层
      -> 读取 Redis 会话运行态
      -> 读取 GoldenDB 任务态和助手记忆
      -> 调用统一知识库获取制度、规则、操作指引和历史经验
      -> 调用 ES / Java API 获取资产事实
      -> 做权限过滤、上下文裁剪和脱敏
  -> LangGraph 多主控编排
  -> 子 Agent / Tool Adapter / LLM
```

这样划分后，LangGraph 不需要自己到处拼上下文，子 Agent 也不需要重复理解用户身份、页面状态和任务状态。

## 6. 单表元数据治理中的上下文流

```text
用户输入：帮我治理 ods_order_detail 这张表
  -> Agent 网关透传 user_id、role、trace_id
  -> 前端透传当前页面、可能选中的资产
  -> 上下文管理层读取会话候选表和用户常用空间
  -> 上下文管理层从统一知识库召回字段命名规范、治理规则和历史确认经验
  -> 数据地图 Tool 获取候选资产
  -> 用户确认唯一表
  -> 上下文管理层固化 asset_context 和 confirmed_slots
  -> 标准 / 血缘 / 安全 SubAgent 补齐 evidence_context
  -> 元数据治理 SubAgent 基于裁剪后的上下文生成候选值
  -> 用户确认治理草案
  -> GoldenDB 写确认记录、任务状态和审计摘要
  -> Activiti 提交流程，调度平台接管后续状态推进
```

这里的关键不是“把所有资料给模型”，而是每一步都明确当前上下文状态，并且只把当前节点真正需要的信息传给模型、子 Agent 或 Tool。

## 7. 和 Redis、GoldenDB、助手记忆的关系

上下文管理层是逻辑能力，Redis、GoldenDB 和助手记忆是它使用的存储与工具。

```text
上下文管理层：负责组织、裁剪、脱敏、传递和沉淀上下文。
统一知识库：提供制度、规则、操作指引、FAQ 和历史经验，是上下文管理层的重要知识来源。
Redis：保存短期会话运行态、临时槽位、候选列表、待确认状态。
GoldenDB：保存任务状态、确认记录、审计摘要、长期记忆。
助手记忆 Tool：读写用户偏好和可复用历史确认经验。
Langfuse / OTel：记录调用链路、模型输入输出摘要和效果反馈。
```

因此，不能把“有 Redis”或“有知识库”理解为“已经有上下文管理”。Redis 是存储介质，知识库是可召回的知识来源，真正需要设计的是上下文的来源、结构、生命周期、权限边界、知识引用和传递规则。

## 8. 建设优先级

### Demo 阶段

1. 定义统一 `context envelope`。
2. 在请求体中模拟 user_context、page_context。
3. 用内存或 Redis 模拟 thread_id、候选表、待确认状态。
4. 用 Mock 助手记忆返回常用空间、项目和开发账号。
5. 接入或模拟统一知识库召回，返回规则说明、字段命名规范和治理口径。
6. 在 Demo 页面展示“已确认资产、待确认动作、当前任务状态和引用知识来源”。

### 一期试点

1. 由 Agent 网关正式透传用户身份和 trace_id。
2. 对接 Redis 管理会话运行态。
3. 对接 GoldenDB 保存确认记录、任务状态、用户偏好。
4. 正式接入统一知识库，按任务类型配置知识召回范围和引用摘要。
5. 建立上下文裁剪、敏感字段脱敏和日志屏蔽规则。
6. 按任务类型沉淀上下文模板：查询、治理、诊断、报告、写操作。

### 平台化阶段

1. 建设统一上下文服务，供数小智下多个专家助手复用。
2. 将统一知识库、历史确认样本和语义召回能力纳入统一上下文服务。
3. 将上下文策略纳入 Agent 网关治理。
4. 支持跨会话、跨任务、跨助手的可控记忆与复用。

## 9. 汇报口径

```text
数据资产助手要补一层上下文管理能力。
它不是简单保存聊天记录，也不是把知识库内容原样塞给模型，而是把用户身份、页面状态、资产对象、任务进度、业务证据、知识库召回、历史偏好和权限策略统一组织起来。
统一知识库已经提供了制度、规则、操作指引和历史经验；上下文管理负责判断本次任务该取哪些知识、如何引用、是否需要裁剪脱敏，以及能否进入模型。
有了上下文管理，Agent 才能知道“用户说的是哪张表、已经确认过什么、该参考哪些知识、还缺什么证据、哪些信息不能给模型、下一步应该交给哪个子 Agent 或 Tool”。
这也是数据资产助手从 Demo 走向生产试点时，必须补齐的企业级能力。
```
