# 08 数据资产助手 Loop 使用判断

## 1. 结论

数据资产助手不是所有场景都要使用 Agent Loop，也不是所有场景都适合固定流程。

推荐采用：

```text
固定流程 / 状态机：负责确定性主流程、写操作、人工确认、权限边界。
Agent Loop：负责不确定问题的动态诊断、多工具探索、证据补齐和答案归纳。
Loop Engineering：负责设计 Loop 的进入条件、工具白名单、停止条件、状态记录和评测标准。
调度系统：负责会话外的异步轮询、失败补偿、超时提醒和批量任务触发。
```

可以简化理解为：

```text
用户问题清楚、流程固定、结果可预期：不用 Loop。
用户目标模糊、需要边查边判断、工具顺序不确定：用 Loop。
涉及写操作、审批、长流程等待：Loop 只能做建议，不能直接越过状态机和调度系统。
```

这里的 Agent Loop 指运行时的 Agentic Loop；Loop Engineering 指对这个运行时循环进行工程设计和治理的方法。前者是“跑起来的循环”，后者是“让循环可控、可测、可复盘的规则体系”。

## 2. Loop 解决什么问题

Loop 的价值不是“循环调用工具”，而是让 Agent 能够根据中间结果动态决定下一步。

典型过程：

```text
观察当前任务和已有证据
判断还缺什么信息
选择下一个只读 Tool 或专家 Agent
执行并读取结果
再次判断是否足够回答
足够则总结，不足则继续，遇到风险或写操作则停止并请求确认
```

因此，Loop 适合处理“路径不确定”的任务，例如治理诊断、问题排查、影响分析、综合评估。

## 2.1 Loop Engineering 解决什么问题

Loop Engineering 的重点不是再发明一个新组件，而是把 Agentic Loop 工程化。它解决的是：

| 问题 | Loop Engineering 的控制方式 |
| --- | --- |
| 什么时候允许进入 Loop | 定义 Prompt 类型、风险等级、参数完整性和只读/写操作边界 |
| Loop 能调用什么 | 维护只读 Tool 白名单，写 Tool 必须转确认节点或状态机 |
| Loop 最多跑多久 | 设置最大步数、最大成本、最大工具调用次数和超时 |
| Loop 如何停止 | 证据足够、发现风险、需要用户确认、连续失败、达到上限即停止 |
| Loop 如何复盘 | 每一步记录任务、工具、入参摘要、返回摘要、证据和 traceId |
| Loop 如何评测 | 用样例集评测工具选择、证据完整性、结论正确性和停止时机 |

因此，Agentic Loop 解决“这一次不确定任务如何边查边判断”；Loop Engineering 解决“这类循环如何被设计、约束、观测和评测”。

## 3. 判断原则

### 3.1 适合使用 Loop 的情况

满足以下任意多项时，可以考虑使用 Loop：

| 判断问题 | 说明 | 示例 |
| --- | --- | --- |
| 用户目标是否模糊 | 用户没有明确说要查哪个固定接口或执行哪个固定动作 | “帮我看看这张表有没有治理问题” |
| 下一步是否依赖上一步结果 | 工具返回后才能判断继续查血缘、标准、安全还是权限 | 先查表详情，发现敏感字段后再查安全等级 |
| 工具调用顺序是否不固定 | 不同资产、不同问题需要不同调用路径 | 有的表需要查血缘，有的表需要查标准，有的表需要查稽核 |
| 是否需要多证据综合判断 | 需要把元数据、标准、血缘、安全、使用热度等拼起来 | 判断一张表能不能下线 |
| 是否属于诊断类任务 | 目标是找原因、找缺口、给建议，而不是提交一个确定流程 | “为什么这张表没人用” |
| 是否需要动态追问 | 信息不足时需要问用户补充表名、系统、环境、时间范围 | 多张同名表需要先消歧 |

### 3.2 不建议使用 Loop 的情况

满足以下情况时，优先使用固定流程、状态机或普通 Tool 调用：

| 判断问题 | 说明 | 示例 |
| --- | --- | --- |
| 用户意图非常明确 | 一次或少量确定接口即可完成 | “查一下 ods_order 的字段列表” |
| 流程顺序稳定 | 每次都按固定步骤推进 | 单表元数据治理流程提交 |
| 涉及写操作 | 必须经过权限校验、参数校验、用户确认、幂等控制 | 提交 Activiti 流程、创建稽核规则 |
| 涉及审批或待办 | 后续状态由流程引擎和调度系统推进 | 治理流程审批、权限申请审批 |
| 涉及长时间等待 | 不能让 Agent Loop 挂起等待外部系统完成 | 安全扫描、元数据采集、稽核任务执行 |
| 规则可枚举且强约束 | 状态转换明确，不应交给模型自由判断 | 数据源登记状态流转 |

## 4. 数据资产场景判断表

| 场景 | 是否用 Loop | 推荐方式 | 原因 |
| --- | --- | --- | --- |
| 数据地图按名称查表 | 不用 | 单次 Tool 调用 + 候选展示 | 用户目标清晰，接口确定 |
| 同名表消歧 | 轻量 Loop / 固定追问 | 查询候选后让用户确认 | 需要根据候选数量决定是否追问 |
| 表字段详情查询 | 不用 | 固定 Tool 调用 | 只读查询，路径确定 |
| 血缘上游/下游查询 | 通常不用 | 固定 Tool 调用 | 用户明确问上游或下游时路径确定 |
| 血缘影响分析 | 可用 Loop | 多轮只读工具探索 | 可能需要查表级、字段级、SQL 任务、下游报表 |
| SQL 注释识别并补全备注 | 可用 Loop | Loop 取证 + 固定草案生成 | 需要先判断 SQL、字段、标准和目标表上下文 |
| 单表元数据治理提交流程 | 不用 Loop 做主流程 | 状态机 + 人工确认 + Activiti | 流程固定且涉及写操作 |
| 单表治理问题诊断 | 用 Loop | 多工具诊断 + 证据汇总 | 需要动态查元数据、标准、血缘、安全、使用情况 |
| 数据标准匹配 | 视情况 | 明确字段不用 Loop，批量诊断可用 Loop | 单字段匹配确定；整表标准缺口分析需要动态判断 |
| 安全等级查询 | 不用 | 固定 Tool 调用 | 明确资产查安全等级，路径确定 |
| 安全风险诊断 | 可用 Loop | 安全扫描 + 权限 + 血缘综合判断 | 风险原因和影响面不确定 |
| 稽核规则创建 | 不用 Loop 做提交 | 固定流程 + 用户确认 | 创建规则是写操作，必须可控 |
| 稽核规则建议生成 | 可用 Loop | 读取字段、标准、历史规则后生成建议 | 规则建议需要多证据综合 |
| 数据源登记 | 不用 Loop 做主流程 | 状态机 + 页面唤醒 + 调度系统 | 登记、审批、采集、绑定流程固定 |
| 数据源接入问题排查 | 可用 Loop | 动态检查登记、连通性、采集、ES 同步状态 | 失败点不确定，需要逐步定位 |
| 权限申请 | 不用 Loop 做提交 | 固定流程 + 用户确认 + 审批 | 涉及权限和审批 |
| 权限问题解释 | 可用 Loop | 查用户权限、字段敏感等级、资产归属 | 需要判断为什么看不到 |
| 指标口径解释 | 可用 Loop | 查指标定义、血缘、标准、引用报表 | 解释需要跨多个上下文 |
| 批量元数据体检 | 混合 | 调度系统触发批量，单个资产内可用 Loop | 批量调度不靠 Loop，单资产诊断可用 Loop |

## 5. 典型用 Loop 场景

### 5.1 表治理体检

用户输入：

```text
帮我看看 dwd_order_detail 这张表有没有治理问题，给个处理建议。
```

推荐 Loop：

```text
第 1 轮：查数据地图，确认表是否存在。
第 2 轮：查元数据详情，判断中文名、字段备注、负责人是否缺失。
第 3 轮：查数据标准，判断字段是否可匹配标准。
第 4 轮：查安全扫描，判断敏感字段和安全等级。
第 5 轮：查血缘和使用情况，判断是否影响下游。
第 6 轮：汇总治理问题、依据和建议，询问是否生成治理草案。
```

这个场景适合 Loop，因为一开始不知道治理问题在哪里，需要边查边决定下一步。

### 5.2 数据源接入失败排查

用户输入：

```text
这个数据源已经登记了，为什么数据地图里还是查不到表？
```

推荐 Loop：

```text
第 1 轮：查数据源登记状态。
第 2 轮：如果登记未完成，返回审批节点和待办人。
第 3 轮：如果登记完成，查连通性检测结果。
第 4 轮：如果连通性通过，查元数据采集任务状态。
第 5 轮：如果采集完成，查 ES 同步状态。
第 6 轮：定位阻塞点，给出下一步处理建议。
```

这个场景适合 Loop，因为失败点可能在登记、审批、连通性、采集、同步、权限中的任意一环。

### 5.3 权限问题解释

用户输入：

```text
为什么我看不到这张表的手机号字段？
```

推荐 Loop：

```text
第 1 轮：查用户对表的权限。
第 2 轮：查字段安全等级和脱敏策略。
第 3 轮：查当前角色是否允许查看敏感字段。
第 4 轮：判断是无表权限、无字段权限、脱敏策略限制，还是环境限制。
第 5 轮：给出解释和申请建议。
```

这个场景适合 Loop，因为用户看到的是一个现象，Agent 需要动态排查原因。

## 6. 典型不用 Loop 场景

### 6.1 明确查表

用户输入：

```text
查一下 dwd_order_detail 的字段列表。
```

推荐方式：

```text
search_data_map_tool
get_asset_detail_tool
返回字段列表
```

这里不需要 Loop，因为目标、工具和输出都很明确。

### 6.2 提交元数据治理流程

用户输入：

```text
把这张表的中文名和备注提交治理流程。
```

推荐方式：

```text
固定流程：
确认唯一表
生成治理草案
用户确认
权限校验
提交 Activiti
写入任务状态
调度系统轮询流程状态
```

这里不能用 Loop 自由提交，因为涉及写操作、流程实例、用户确认和审计。

### 6.3 创建稽核规则

用户输入：

```text
给 amount 字段创建非空校验规则，每天凌晨执行。
```

推荐方式：

```text
固定流程：
解析规则草案
校验字段和权限
展示调度频率和告警配置
用户确认
创建规则
注册或关联调度计划
```

这里可以用模型生成规则草案，但创建动作必须走固定流程。

## 7. 混合模式

很多数据资产场景不是纯 Loop，也不是纯固定流程，而是混合模式。

推荐模式：

```text
Graph 控制主流程
Loop 负责只读诊断和动态路由
Confirm 节点负责人工确认
Tool Adapter 负责确定性接口调用
调度系统负责异步轮询和补偿
```

示例：单表治理

```text
1. Graph 固定进入“治理诊断”阶段。
2. Loop 动态查询元数据、标准、血缘、安全、使用情况。
3. Loop 汇总证据，生成治理建议。
4. Graph 进入“草案确认”节点。
5. 用户确认后，固定流程提交 Activiti。
6. 调度系统轮询流程状态并回写 agent_task。
```

这样既保留了智能诊断能力，又不会让模型自由越过生产控制边界。

## 8. Loop 使用控制规则

为了避免 Loop 失控，建议加以下约束：

| 控制项 | 建议 |
| --- | --- |
| 最大步数 | 一般 6 到 8 步，复杂诊断不超过 10 步 |
| 工具范围 | 默认只允许只读 Tool；写 Tool 必须进入确认节点 |
| 权限边界 | 每次 Tool 调用前都做用户身份、角色、数据权限校验 |
| 停止条件 | 证据足够、用户需要确认、发现高风险、达到最大步数、工具连续失败 |
| 审计记录 | 每一步记录 step、tool、入参摘要、返回摘要、trace_id |
| 成本控制 | 对高成本 Tool 设置调用次数限制和缓存 |
| 敏感数据 | 密码、Token、连接串、敏感样例值不得进入模型上下文 |
| 可恢复性 | Loop 的关键中间状态写入 agent_task_step 或运行态状态 |

## 9. 评审口径

可以对外这样说明：

```text
数据资产助手会采用“Graph + Loop + 调度系统”的组合方式。

Graph 负责确定性主流程、关键节点、人工确认和状态恢复；
Loop 负责只读场景下的动态诊断、多工具路由和证据补齐；
调度系统负责会话外长流程的轮询、补偿、提醒和批量触发。

因此，不是所有场景都用 Loop。
明确查询、固定流程、写操作、审批流不用 Loop 做主控；
治理诊断、影响分析、问题排查、综合评估这类路径不确定的场景才使用 Loop。
```

## 10. 一句话判断

```text
如果下一步动作可以在设计阶段写死，用固定流程；
如果下一步动作必须看中间结果再决定，用 Loop；
如果下一步动作要等外部系统过一段时间返回，用调度系统。
```
