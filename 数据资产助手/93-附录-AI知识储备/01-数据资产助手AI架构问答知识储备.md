## 1. 为什么现在不强调传统意图识别

### 1.1 问题

为什么现在很多 AI 助手方案里不再把“意图识别”作为核心模块？

### 1.2 核心结论

不是意图识别没有用了，而是它从独立的 `Intent Classifier` 变成了 `Prompt Router + Control Mode Router + Tool Calling + Workflow` 体系里的一个辅助判断。

传统机器人通常是：

```text
用户输入
识别 intent
抽取槽位
进入固定流程
返回结果
```

数据资产助手更适合采用：

```text
用户输入
判断 Prompt 类型、风险等级、关键参数
选择主控模式
执行 Skill / Tool / 状态机 / Agentic Loop / 调度 / 人工确认
返回文本、卡片、表格或任务状态
```

### 1.3 原因

1. 真实用户表达往往不是单一意图，而是混合了目标、背景、现象、限制条件和隐含诉求。
2. 细粒度 intent 数量一多，训练语料、边界规则和冲突处理成本会很高。
3. LLM 可以直接做语义理解、任务拆解、风险判断和工具选择，不再只负责分类。
4. 企业流程更依赖状态、权限、审计和流程节点，而不是只依赖一个 intent 标签。
5. 系统更关心“下一步该调用什么 Tool 或进入什么流程”，而不是只给用户一句话贴标签。

### 1.4 在数据资产助手中的设计口径

数据资产助手可以保留轻量意图判断，但不建立庞大的传统 intent 体系。

推荐口径：

```text
轻量意图识别：负责粗分类、风险识别、入口路由。
Prompt Router：判断用户问题属于说明、查询、办理、诊断、生成、调度、确认还是转交。
Control Mode Router：选择 Skill、Tool、状态机、Loop、流式生成、调度任务、人工确认或子 Agent。
状态机和流程引擎：承接写操作、审批、登记、提交等确定性流程。
```

### 1.5 Control Mode Router 的具体含义

`Control Mode Router` 可以理解为“执行模式路由器”或“主控模式路由器”。

它不只是判断用户在问什么，而是判断这个问题应该交给哪一种执行方式来处理。

传统意图识别更关注：

```text
用户想做什么？
```

Control Mode Router 更关注：

```text
这个请求应该怎么被安全、稳定、可审计地执行？
```

也就是说，它的输出不是一个简单的 `intent = xxx`，而是一个执行控制决策。

例如：

| 用户输入 | Prompt Router 判断 | Control Mode Router 选择 |
| --- | --- | --- |
| 解释一下 SSE 是什么 | 说明类问题 | Skill 问答 / 知识库问答 |
| 查一下 dwd_order_detail 的字段 | 明确查询类问题 | 单次 Tool 查询 |
| 帮我治理这张表的元数据 | 办理类 / 治理类问题 | 固定状态机 + 元数据治理 Agent |
| 这张表为什么安全等级异常 | 诊断类问题 | Agentic Loop + 只读 Tool |
| 生成一份治理报告 | 长文本生成类问题 | 流式生成控制器 |
| 提交治理结果 | 写操作 / 高风险动作 | 人工确认 + 状态机 |
| 等扫描结果出来后提醒我 | 异步等待类问题 | 调度任务控制器 |

### 1.6 为什么需要 Control Mode Router

因为数据资产助手不是只有一种回答方式。

如果所有请求都默认进入 Agentic Loop，会出现几个问题：

| 问题 | 说明 |
| --- | --- |
| 简单问题被复杂化 | 明确查表、解释概念不需要多轮推理和多次工具调用 |
| 写操作风险变高 | 模型不能直接决定提交、修改、审批、绑定等动作 |
| 长流程难以挂起 | 等流程、等采集、等扫描不适合靠会话里的 Loop 一直等 |
| 审计边界不清楚 | 事后很难解释为什么选择了某个执行路径 |
| 成本和性能不可控 | 所有请求都跑 Agentic Loop，会增加模型调用、Tool 调用和延迟 |

Control Mode Router 的价值是：把“LLM 理解能力”放进一个可控执行框架里。

它负责回答：

```text
这次请求是说明、查询、办理、诊断、生成、调度、确认，还是转交？
是否需要调用工具？
是否允许进入 Agentic Loop？
是否涉及写操作或高风险动作？
是否必须走状态机、人工确认或调度系统？
最终应该返回文本、卡片、表格、任务状态，还是确认弹窗？
```

### 1.7 在数据资产助手中的推荐主控模式

| 主控模式 | 适用场景 | 典型例子 |
| --- | --- | --- |
| `skill_qa` | 稳定概念解释、方法论说明 | SSE 是什么、Agent 网关是什么 |
| `tool_query` | 参数明确、一次查询即可完成 | 查表详情、查字段、查血缘 |
| `state_machine` | 步骤确定、需要流程状态推进 | 数据源登记、元数据治理提交 |
| `agentic_loop` | 路径不确定、需要边查边判断 | 异常诊断、影响分析、治理体检 |
| `streaming` | 长文本生成、报告生成 | 生成治理报告、评审说明 |
| `scheduler` | 会话外异步等待、批量、定时、补偿 | 等扫描结果、批量补全、超时提醒 |
| `human_confirm` | 写操作、高风险动作 | 提交审批、写回备注、修改安全等级 |
| `handoff` | 需要转给其他专家 Agent | 转给数据权限、数据标准、安全扫描 Agent |

### 1.8 一句话口径

```text
Control Mode Router 是数据资产助手的执行模式路由器，它不只是识别用户意图，而是根据任务类型、风险等级、参数完整性和流程状态，选择 Skill、Tool、状态机、Loop、流式生成、调度、人工确认或子 Agent 转交等最合适的执行方式。
```

## 2. 什么是流式生成控制器

### 2.1 问题

应用架构图里的“流式生成控制器”是什么？

### 2.2 核心结论

流式生成控制器是数据资产助手的一种主控模式，负责在证据基本齐全后生成较长的报告、总结、说明或评审口径，并将内容分段返回给前端。

它不是业务系统，也不是 Tool Adapter，而是 AI 助手服务里的输出控制器。

### 2.3 典型场景

```text
生成治理报告
整理评审口径
生成问题诊断总结
输出血缘影响分析说明
生成元数据治理建议说明
```

例如：

```text
用户：帮我生成 dwd_order_detail 这张表的治理评审说明。
```

推荐链路：

```text
Prompt Router 判断为“报告 / 总结 / 说明生成”
Control Mode Router 选择流式生成控制器
前置 Tool / Agent 已拿到表信息、字段问题、标准匹配、安全等级、血缘影响
流式生成控制器组织 Prompt 并调用 LLM
FastAPI 通过 Streaming / SSE 分段返回
前端实时展示生成内容
```

### 2.4 职责边界

流式生成控制器负责：

```text
组织生成上下文
拼装报告生成 Prompt
调用大模型生成长文本
控制输出节奏
把内容通过 Streaming / SSE 返回前端
记录生成 trace 和反馈
```

不负责：

```text
提交审批
修改生产数据
长时间轮询外部系统
自由调用大量 Tool 做动态排查
绕过人工确认执行高风险动作
```

一句话口径：

```text
流式生成控制器是面向长文本生成场景的输出控制器，负责把已有证据组织成报告、总结、说明，并通过流式方式返回给用户。
```

## 3. 什么是 SSE

### 3.1 问题

SSE 是什么？为什么数据资产助手的流式生成可以用 SSE？

### 3.2 核心结论

SSE 是 `Server-Sent Events`，中文可以理解为服务器推送事件。它基于普通 HTTP 连接，由服务端持续向浏览器推送数据。

普通 HTTP：

```text
前端请求
后端处理完成
一次性返回完整结果
```

SSE：

```text
前端请求
后端保持连接
后端持续推送多段内容
前端边接收边展示
```

### 3.3 在数据资产助手中的用法

```text
用户请求生成治理报告
后端开始调用 LLM
LLM 每生成一段内容
FastAPI 通过 SSE 推送给前端
前端逐段展示
生成完成后发送 done 事件
```

示例事件：

```text
event: message
data: 正在整理资产基本信息...

event: message
data: 正在分析字段备注缺失情况...

event: message
data: 正在生成治理建议...

event: done
data: 完成
```

### 3.4 SSE 与 WebSocket 的区别

| 对比项 | SSE | WebSocket |
| --- | --- | --- |
| 通信方向 | 服务端向前端推送为主 | 双向通信 |
| 底层协议 | HTTP | WebSocket |
| 适合场景 | 流式回答、进度推送、日志推送 | 实时协作、双向控制、在线游戏 |
| 实现复杂度 | 较低 | 较高 |
| 浏览器能力 | EventSource 原生支持 | WebSocket 原生支持 |

数据资产助手的流式回答、报告生成、任务进度提示更偏服务端向前端推送，优先用 SSE 更简单。

## 4. Redis 存运行态，为什么 GoldenDB 不直接存

### 4.1 问题

既然 GoldenDB 也能存数据，为什么会话运行态要放 Redis，而不是都放 GoldenDB？

### 4.2 核心结论

GoldenDB 可以存，但不建议把高频、短生命周期、可过期、可重建的运行态主要放 GoldenDB。

推荐分工：

```text
Redis：存正在发生什么。
GoldenDB：存最终发生了什么、需要留痕什么。
```

### 4.3 Redis 适合存什么

```text
当前 thread_id 对应的会话上下文
临时槽位
候选表列表
等待确认的临时状态
本轮 Tool 调用的临时结果
短期任务进度
前端轮询或刷新需要的运行态
```

这些数据通常生命周期短、访问频率高、可设置 TTL、过期后可以重新查询或重新生成。

### 4.4 GoldenDB 适合存什么

```text
用户最终确认记录
治理草案版本
是否点击提交
Activiti 流程实例 ID
任务最终状态
失败原因
审计摘要
助手记忆
用户常用项目、空间、开发账号等偏好
```

这些数据需要持久化、审计、追溯、复盘或支撑报表查询。

### 4.5 推荐落库策略

| 状态类型 | Redis | GoldenDB |
| --- | --- | --- |
| 当前会话上下文 | 是 | 可选摘要 |
| 临时槽位 | 是 | 否 |
| 候选表列表 | 是 | 用户确认后存关键结果 |
| 等待确认状态 | 是 | 重要确认单也存 |
| 用户确认记录 | 可缓存 | 是 |
| 任务最终状态 | 可缓存 | 是 |
| 流程实例 ID | 可缓存 | 是 |
| 审计摘要 | 否 | 是 |
| 助手记忆 | 可缓存 | 是 |
| LLM 中间 token | 通常不存 | 通常不存 |

推荐过程：

```text
会话开始：Redis 建运行态
用户确认：GoldenDB 写确认记录
提交流程：GoldenDB 写 task / process_instance_id
执行中：Redis 缓存进度，GoldenDB 落关键状态
完成或失败：GoldenDB 写最终结果，Redis 设置短 TTL
```

### 4.6 设计口径

```text
Redis 不是替代 GoldenDB，而是承接对话执行过程中的短期运行态。
GoldenDB 不是不能存运行态，而是不适合承接大量高频临时状态。
关键节点需要落库留痕，临时上下文放 Redis 提升性能和清晰度。
```

## 4.5 上下文管理为什么要单独设计

### 4.5.1 问题

既然已经有 Redis 存会话运行态，也有 GoldenDB 存助手记忆，为什么还要单独讲“上下文管理”？

### 4.5.2 核心结论

Redis 和 GoldenDB 解决“存在哪里”，上下文管理解决“什么信息该被组织、裁剪、脱敏、传递和沉淀”。

推荐口径：

```text
上下文管理不是一个数据库，而是一层 Context Engineering 能力。
它决定当前任务需要哪些上下文、哪些上下文可以给模型、哪些只能给 Tool、哪些必须留痕、哪些必须丢弃或脱敏。
```

### 4.5.3 上下文管理解决什么问题

| 问题 | 如果没有上下文管理 | 上下文管理的作用 |
| --- | --- | --- |
| 指代不清 | 用户说“这张表”，助手不知道指哪个对象 | 结合页面态、候选表、已确认资产确定对象 |
| 重复追问 | 已确认过空间、项目、开发账号仍反复问 | 从记忆和 confirmed slots 中恢复已知信息 |
| 证据分散 | 标准、血缘、安全、质量各查各的 | 形成统一 evidence_context 给治理 Agent 使用 |
| 模型上下文过大 | 全量字段、SQL、血缘都塞给模型 | 按任务类型裁剪和摘要 |
| 安全风险 | token、连接串、敏感样例进入模型或日志 | 做权限过滤、脱敏和模型可见范围控制 |
| 长流程恢复困难 | 只有 task_id，缺少当时的资产和确认记录 | 通过 task_context 恢复任务现场 |

### 4.5.4 推荐上下文分层

数据资产助手至少要管理这些上下文：

```text
trace_context：trace_id、thread_id、task_id。
user_context：用户、组织、角色、权限。
page_context：当前页面、选中资产、筛选条件。
asset_context：数据源、schema、表、字段、负责人。
task_context：任务类型、状态、已确认槽位、待确认动作。
evidence_context：标准、血缘、安全、质量、流程证据。
memory_context：常用空间、项目、开发账号、历史确认偏好。
policy_context：允许工具、禁止工具、是否需要人工确认、脱敏规则。
```

其中：

```text
Prompt Router 需要轻量上下文。
Control Mode Router 需要任务类型、风险等级和参数完整性。
子 Agent 需要专业上下文和证据。
Tool Adapter 需要接口参数、token、trace_id 和审计字段。
LLM 只需要脱敏后的问题、证据摘要、输出约束和解释依据。
```

### 4.5.5 与 Redis、GoldenDB、助手记忆的关系

```text
上下文管理层：负责组织、裁剪、脱敏、传递和沉淀。
Redis：保存短期会话运行态、临时槽位、候选列表、待确认状态。
GoldenDB：保存任务状态、用户确认、审计摘要、长期偏好。
助手记忆 Tool：读写用户常用空间、项目、开发账号等可复用偏好。
Langfuse / OTel：记录调用链路、模型输入输出摘要和效果反馈。
```

所以，不能把“有 Redis”理解成“已经有上下文管理”。Redis 只是上下文管理使用的存储介质之一。

### 4.5.6 汇报口径

```text
数据资产助手要补一层上下文管理能力。
它不是简单保存聊天记录，而是把用户身份、页面状态、资产对象、任务进度、业务证据、历史偏好和权限策略统一组织起来。
有了上下文管理，Agent 才能知道用户说的是哪张表、已经确认过什么、还缺什么证据、哪些信息不能给模型、下一步应该交给哪个子 Agent 或 Tool。
```

## 5. 为什么需要加上调度系统

### 5.1 问题

既然已经有 LangGraph / Agent 编排，为什么还需要单独引入调度系统？

### 5.2 核心结论

调度系统不是用来替代 Agent 的，而是用来承接“会话外”的长时间异步任务。

推荐口径：

```text
LangGraph / Agent 负责当前这次用户请求怎么拆、调什么工具、是否需要确认。
调度系统负责任务提交后是否完成、失败后是否补偿、超时后是否提醒、批量任务何时触发。
```

如果没有调度系统，Agent 很容易被迫承担它不擅长的事情：长时间挂起、定时轮询、失败重试、批量触发和超时通知。这些能力本质上更接近工程调度和任务治理，而不是大模型推理。

### 5.3 不加调度系统的问题

| 问题 | 影响 |
| --- | --- |
| Agent 会话不适合长时间等待 | 用户关闭页面、服务重启或会话过期后，任务推进容易中断 |
| 大模型不适合做周期性轮询 | 轮询 Activiti、采集任务、安全扫描、稽核任务会浪费模型资源 |
| 失败补偿缺少统一入口 | 接口超时、回调丢失、下游失败后，难以自动恢复 |
| 超时提醒难以治理 | 待确认、待审批、待处理任务无法形成稳定提醒机制 |
| 批量任务缺少触发器 | 批量元数据补全、批量安全扫描、批量体检不适合靠用户会话驱动 |

### 5.4 在数据资产助手中的职责

调度系统主要承接这些事情：

```text
Activiti 流程状态轮询
元数据采集完成检查
数据地图 / ES 同步状态检查
安全扫描任务完成检查
数据稽核任务完成检查
批量智能元数据补全触发
待确认 / 待审批任务超时提醒
失败任务补偿、重试和告警
```

对应到数据资产助手，可以形成三层分工：

```text
LangGraph：会话内编排，负责当前用户请求的理解、拆解、工具选择和确认节点。
调度系统：会话外推进，负责异步轮询、定时触发、失败补偿和超时提醒。
GoldenDB：任务账本，负责 agent_task、agent_task_step、确认记录和最终状态留痕。
```

### 5.5 设计边界

调度系统应该做：

```text
根据 task_id 恢复任务上下文
轮询外部流程或异步任务状态
回写 agent_task / agent_task_step
触发补偿、重试、提醒或告警
必要时唤醒助手服务继续执行下一步
```

调度系统不应该做：

```text
直接替代 LangGraph 做语义理解
直接调用大模型自由生成方案
绕过 Agent 的确认策略执行写操作
绕过业务系统权限修改生产数据
```

一句话口径：

```text
调度系统是数据资产助手的会话外任务推进器，解决长流程、异步等待、失败补偿、超时提醒和批量触发问题。
```

## 6. 为什么需要建设 Agent 网关

### 6.1 问题

既然现有数据资产平台已经有 Gateway，AI 助手内部也可以直接写 Tool Adapter，为什么还要建设 Agent 网关？

### 6.2 核心结论

现有 Gateway 主要管理“人访问业务系统”的入口；Agent 网关管理“Agent 访问工具、MCP、子 Agent 和业务能力”的入口。

它不是重复建设一个业务网关，而是在 AI 能力侧增加一层可治理的调用边界。

推荐口径：

```text
业务 Gateway 负责用户认证、统一入口、身份透传和业务系统访问控制。
Agent 网关负责 Tool / MCP / 子 Agent 的注册发现、权限策略、参数校验、风险控制、版本路由、限流熔断、可观测和审计。
```

### 6.3 Agent 网关解决什么问题

| 问题 | Agent 网关的作用 |
| --- | --- |
| 工具越来越多 | 统一注册、发现、描述和版本管理 |
| 多个 Agent 复用同一能力 | 避免每个 Agent 都重复封装数据地图、安全扫描、数据标准等接口 |
| 工具调用风险不一致 | 统一区分只读、写入、高风险动作和必须人工确认的动作 |
| 参数格式不稳定 | 统一 Schema 校验、默认值处理、错误码转换 |
| 权限容易散落 | 统一身份透传、角色校验、工具白名单和数据权限判断 |
| 观测链路断裂 | 统一记录 trace_id、thread_id、task_id、tool_name、耗时和结果摘要 |
| 下游不稳定 | 统一限流、熔断、重试、超时和幂等控制 |

### 6.4 在数据资产助手中的位置

建议理解为：

```text
数小智 / 数据资产助手
  -> Agent 网关
  -> Tool Registry / MCP Server / Tool Adapter
  -> 现有数据资产 Gateway / Java API / ES / Activiti / 调度平台
```

也就是说，Agent 网关不绕过现有平台能力，而是把 AI 侧的调用统一收口，再通过受控方式访问现有 Java API、数据地图、标准中心、安全扫描、调度平台和流程引擎。

### 6.5 Agent 网关应该具备的能力

一期可以轻量建设，不需要一开始就做成完整平台。

| 阶段 | 建设重点 | 说明 |
| --- | --- | --- |
| Demo 阶段 | Tool Registry + 策略校验 | 当前 Demo 中的工具注册、工具描述、Mock 调用和风险标记，就是 Agent 网关的雏形 |
| 首期落地 | 统一工具入口 + 身份透传 + 审计 | 将数据地图、安全扫描、数据标准、元数据补全等能力统一封装 |
| 平台化阶段 | MCP 网关 / Agent Gateway | 支持多 Agent 复用、统一版本、统一观测、统一灰度和统一安全策略 |

### 6.6 与 MCP、Tool、Skill 的关系

```text
Tool：一个可调用的原子能力，例如查询表详情、匹配数据标准、发起安全扫描。
Skill：一套稳定的方法论、Prompt 模板和业务规则，例如元数据补全判断逻辑。
MCP：一种工具协议和服务化封装方式，让多个 Agent 以标准方式调用工具。
Agent 网关：AI 侧工具和子 Agent 调用的治理入口，负责注册、策略、路由、观测和审计。
```

因此，Agent 网关不是和 MCP 二选一。更合理的关系是：早期用 Tool Registry 和 Tool Adapter 实现 Agent 网关雏形，后续把稳定、高复用的工具逐步 MCP 化，再由 Agent 网关统一管理。

### 6.7 设计边界

Agent 网关应该做：

```text
统一工具注册和描述
统一身份透传和权限校验
统一参数 Schema 校验
统一风险策略和人工确认规则
统一限流、熔断、超时、重试和幂等
统一 trace、审计和调用日志
统一测试 / 生产环境路由
```

Agent 网关不应该做：

```text
替代现有数据资产管理 Gateway
替代业务系统自身权限控制
替代 Activiti 等流程引擎
替代调度系统做长流程轮询
允许模型绕过确认直接执行高风险写操作
```

一句话口径：

```text
Agent 网关是 AI 能力侧的统一调用治理层，解决多 Agent、多工具、多系统接入后的注册、权限、风险、观测和审计问题。
```

## 7. 可复用汇报口径

数据资产助手不是传统的“意图识别 + 固定问答”机器人，而是采用多主控模式的 AI 编排架构。

其中：

```text
Prompt Router 负责理解问题类型和风险。
Control Mode Router 负责选择执行模式。
上下文管理层负责组织用户、页面、资产、任务、证据、记忆和权限上下文。
Skill 问答负责规则说明。
单次 Tool 负责明确查询。
固定状态机负责办理、提交、创建、审批等确定性流程。
Agentic Loop 负责诊断、排查、影响分析等路径不确定任务。
流式生成控制器负责报告、总结、说明等长文本生成。
调度任务控制器负责异步等待、批量、定时和补偿。
Agent 网关负责统一管理 Agent 到 Tool / MCP / 子 Agent 的调用、策略、鉴权、观测和审计。
人工确认控制器负责写操作和高风险动作拦截。
Redis 负责短期运行态，GoldenDB 负责持久任务态、确认、审计和助手记忆。
```

一句话总结：

```text
数据资产助手的核心不是把所有问题都归成 intent，也不是让模型自由执行所有动作，而是把 LLM 的理解和生成能力放到可控的 Tool、状态机、调度、确认和审计体系中。
```
